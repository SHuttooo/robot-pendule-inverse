# Simulation and learning

**English** · [Français](README.fr.md)

The robot rebuilt in MuJoCo from its SolidWorks assembly, the firmware's dual
PID ported as-is as a reference, and a PPO policy trained to beat it, then
exported to C for the ESP32. Script names and code comments are in French.

**Run every script from this folder.**

```
pip install -r requirements.txt
pip install torch --index-url https://download.pytorch.org/whl/cpu
```

---

## The robot model

**`modeles/balancier.xml`**: the robot in MJCF, MuJoCo's XML format. It is
generated by `modele.py`, never edited by hand, and loads the meshes from
`hardware/cao/stl_assemblage/`. This file uses MuJoCo's simple velocity
actuator; the faithful stepper motor model used for training is added by
`modele.xml('couple')` and `moteur.py`.

There is no URDF: nothing in this project uses ROS.

## The principle

A policy trained on a wrong model learns to balance a robot that does not
exist, and nobody notices until the transfer. So the model is validated
**before** training, and every value records where it comes from:

```
python modele.py --etat
```

`MESURE` (measured on the robot, from a datasheet or the assembly), `DEDUIT`
(derived from a measurement), `ESTIME` (estimated), `SUPPOSE` (assumed). 2 of
the 24 parameters are still not established.

The geometry is not typed in: the 6 STL files in
`hardware/cao/stl_assemblage/` carry the mass, and MuJoCo computes the inertia
from the actual shape.

## The motor, the part that changed everything

A stepper motor is not a speed source. It is a **magnetic spring** between the
commanded position and the rotor position:

```
T = T_holding · sin(50 · (θ_command − θ_rotor))
```

This spring resonates. The resonance was **measured at 71 Hz** on the robot, not
the 113 Hz assumed at first, using frequency sweeps injected in closed loop and
cross-spectra, without taking the robot apart. With MuJoCo's `<velocity>`
actuator, the old policy looked perfect. On the robot, it shook ten times more.
With `moteur.py`, the simulation reproduces that shaking to within 1% on the
command, without ever being fitted to it.

## Train, export, flash

```
python 07_ppo.py --actionneur couple --pas 9000000
python 08_agent.py --duel
python 11_export_c.py --agent agents/balancier_final.zip
python 12_valider_c.py
```

The final policy was trained in 15.7 min for 9 M steps (Ryzen 7 7800X3D,
16 environments, CPU only). `12_valider_c.py` must report a difference around
10⁻⁷: that is the float32 / float64 difference, nothing else. **Never flash a
header that has not been through it**: a transposed matrix shows up no other way
than by watching the robot fall.

### Versioned policies

| | |
|---|---|
| `agents/balancier_final.zip` | the current policy, trained on the faithful motor. This is the one in `politique.h`. |
| `agents_v1_vitesse/balancier_9000000_pas.zip` | the old one, trained on the velocity actuator. Kept for comparison (`film.py --comparer`). |

Intermediate checkpoints, training logs and renders are not versioned: they can
be regenerated.

## Results

All evaluated on the faithful motor, robot at rest:

| | old policy | **new policy** | dual PID |
|---|---|---|---|
| tilt error, standard deviation | 1.743° | **0.106°** | 0.185° |
| command, standard deviation | 873 steps/s | **47 steps/s** | 86 steps/s |
| position drift | 55 mm | 12 mm | 13 mm |
| survival at difficulty 1.0 | 25% | **42%** | 33% |

Single 150 ms push, 21 cm above the axle (`17_pousser_agents.py`): dual PID
0.47 N, old policy 0.38 N, new policy 0.53 N. **But this advantage does not
survive a sequence of pushes**: at 0.55 N both fall, at 0.50 N both hold. So the
video shows no difference in push resistance, because there is no robust one.
What it does show is the real difference: the shaking.

Every number is detailed in [`docs/journal/RESULTATS.md`](../docs/journal/RESULTATS.md),
the mistakes made along the way in [`docs/journal/PIEGES.md`](../docs/journal/PIEGES.md)
(both in French).
